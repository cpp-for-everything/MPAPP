# T-0003 — Windows App SDK dependency-resolution choices

This note documents how `examples/windows_button_spike/` acquires the Windows App SDK / C++/WinRT toolchain at build time, and why each call-out in [[../T-0003-winui3-button-spike]] looks the way it does. Future MPAPP Windows handlers (Label, Entry, …) will inherit this setup verbatim.

## What we needed

- **C++/WinRT projection** for the WinUI 3 type surface (`winrt::Microsoft::UI::Xaml::Controls::Button`, `TextBlock`, etc.).
- **Bootstrap library** to load the unpackaged Windows App Runtime (`MddBootstrap*` APIs).
- **WindowsAppRuntime DLL** for the undocked reg-free WinRT manifest (without it, `Application::Start` cannot activate XAML types in an unpackaged app — see [[rpc-e-wrong-thread]]).
- **Runtime DLLs alongside the EXE** (`Microsoft.WindowsAppRuntime.dll`, `Microsoft.WindowsAppRuntime.Bootstrap.dll`) so the loader can resolve our imports before `main` runs.

## Options considered

| Option | Outcome |
|---|---|
| MSBuild project + `<PackageReference>` | Mature but pulls in IDE-only tooling. Conflicts with MPAPP's [[CI Strategy]] which standardises on Ninja. Rejected. |
| `vcpkg install microsoft-windows-app-sdk` | No port in mainline vcpkg today; private port would re-implement the NuGet glue. Rejected for now. |
| `FetchContent` from the WindowsAppSDK self-contained redistributable ZIP | Works for the runtime DLLs but the ZIP doesn't ship cppwinrt.exe or the WinMD files for the projection. Would need a second source for those. Rejected. |
| **`nuget.exe` + a CMake helper module** | What we did. Self-contained: the helper downloads `nuget.exe` on first run, restores `Microsoft.Windows.CppWinRT` and `Microsoft.WindowsAppSDK` to `build/packages/`, generates the projection with `cppwinrt.exe`, and post-build copies the runtime DLLs. No IDE dependency. |

## What's in the chosen path

- `cmake/WindowsAppSDK.cmake` — exposes:
  - `mpapp_install_windows_app_sdk()` — restores NuGet packages (idempotent, cached in `build/packages/`).
  - `mpapp_generate_winrt_projection(<target> <out_var>)` — runs `cppwinrt.exe` at configure time so the headers exist before the dependency-scanning pass; also wires an `add_custom_command` so subsequent SDK upgrades regenerate the projection.
  - `mpapp_add_winappsdk_runtime(<target>)` — sets include paths, link libs (`Microsoft.WindowsAppRuntime.Bootstrap.lib`, `Microsoft.WindowsAppRuntime.lib`, `cppwinrt_fast_forwarder.lib`, `windowsapp.lib`), and the post-build DLL copy step.

- `examples/windows_button_spike/CMakeLists.txt` — uses the helper for the unpackaged-WinUI 3 EXE; the `mpapp-handlers-windows` static library reuses the same projection include path so its translation units (the actual button/label handlers) get the cppwinrt headers without owning the SDK setup themselves.

## Versions pinned

- `Microsoft.Windows.CppWinRT` **2.0.250303.1** — latest stable at spike time.
- `Microsoft.WindowsAppSDK` **1.8.260416003** — chosen because the matching `Microsoft.WindowsAppRuntime.1.8` framework package is preinstalled on Windows 11 24H2 development images. Bumping to 2.x is a follow-up RFC once the 2.x runtime ships preinstalled.
- `cppwinrt -in 10.0.26100.0` — Windows SDK 26100 ships in VS 18 (the active toolchain).

## File layout under `build/`

```
build/
├── nuget/nuget.exe                       (downloaded once)
├── packages/                             (NuGet cache, .gitignored)
│   ├── Microsoft.Windows.CppWinRT/
│   ├── Microsoft.WindowsAppSDK*/
│   └── Microsoft.Web.WebView2/           (transitive — WinUI references WebView2)
├── winrt_projection/                     (generated by cppwinrt)
│   └── winrt/                            (the actual cppwinrt headers)
└── examples/windows_button_spike/
    ├── windows_button_spike.exe
    ├── Microsoft.WindowsAppRuntime.Bootstrap.dll  (copied)
    └── Microsoft.WindowsAppRuntime.dll            (copied)
```

## Known pitfalls (do not regress)

1. `cppwinrt.exe` writes headers directly into `<out>/winrt/`, not `<out>/include/winrt/`. The include path passed to the compiler is `<out>` itself.
2. The projection must reference Microsoft.Web.WebView2's WinMD (it ships at `Microsoft.Web.WebView2/lib/Microsoft.Web.WebView2.Core.winmd`) — `IWebView2`'s `CoreWebView2` member references that namespace.
3. The C++/WinRT dependency-scanning pass (`-scanDependencies`) runs BEFORE custom commands, so the projection has to exist at configure time. The helper runs `cppwinrt.exe` synchronously via `execute_process` on the first configure, then sets up the `add_custom_command` for subsequent regeneration.
4. `windowsapp.lib` is required; `runtimeobject.lib` (the UWP equivalent) is NOT — including it caused subtle link-time conflicts and was removed.
